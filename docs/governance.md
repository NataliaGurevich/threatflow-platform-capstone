# ThreatFlow data governance and responsible use

## Scope and ownership

ThreatFlow processes public vulnerability intelligence:

| Dataset | Responsible publisher | Project use |
| --- | --- | --- |
| NVD | US National Institute of Standards and Technology | CVE description, modification time, CVSS, CWE and references |
| CISA KEV | US Cybersecurity and Infrastructure Security Agency | Confirmed-exploitation and remediation context |
| EPSS | FIRST EPSS SIG; scores generated by Empirical Security | Daily exploitation probability and percentile |

ThreatFlow does not alter the meaning of source signals and does not present itself as an
official NIST, CISA, DHS or FIRST product.

## Access, licence and attribution

- NVD is accessed through its public API. Clients must respect published API guidance,
  throttling and service availability. An optional API key is an operational credential.
- The official `cisagov/kev-data` repository states that the KEV database is released under
  CC0 1.0. That permission does not grant use of CISA/DHS logos or imply endorsement, and
  third-party links retain their own terms.
- EPSS publishes scores freely without registration and requests attribution when the data
  is used in publications or products. The batch pipeline uses the daily CSV/archive rather
  than abusing the lookup-oriented API for bulk synchronization.
- Project documentation should link to the original publishers and state the acquisition
  date when presenting time-sensitive results.

This is an engineering summary, not legal advice. Source terms should be reviewed again
before commercial redistribution or a public production deployment.

## Privacy and sensitivity

The selected fields describe publicly disclosed software vulnerabilities and contain no
intended personal data. Under the current scope, GDPR personal-data processing is not a
central risk.

Security relevance does not make the feed confidential, but operational extensions can
change the classification. Future asset inventory, installed versions, exposure, business
criticality, remediation status or incident data would reveal an organisation's security
posture and must be access-controlled, minimised and assigned an explicit retention policy.

## Access control

- Ingestion services require write access to application tables and Raw storage.
- Airflow metadata remains logically separate from application data.
- Metabase uses a dedicated read-only analytics principal for ThreatFlow data and a separate
  database/user for its own application metadata.
- Developers should use isolated disposable databases for destructive tests.
- Production/staging data, volumes or schemas must not be dropped or reset as part of a demo.
- A future cloud deployment must use least-privilege task roles, private database access,
  encryption in transit/at rest and auditable access logs.

## Credentials and configuration

- `.env` is excluded from Git; `.env.example` contains placeholders only.
- PostgreSQL, Airflow and Metabase passwords and the Airflow JWT secret are injected through
  environment configuration.
- Optional NVD and GitHub tokens are never logged or stored in Raw manifests.
- Credentials must not be placed in DAG source, command-line history, analytical SQL,
  screenshots or documentation.
- Cloud deployment should replace long-lived credentials with IAM roles and store remaining
  secrets in an appropriate secret manager.

## Retention and deletion

| Data | Current policy | Rationale |
| --- | --- | --- |
| Exact Raw artifacts | Retained; no automatic local deletion | Required for replay, audit and parser changes |
| `raw_artifacts` manifest | Retained | Provenance and observation history |
| `nvd_cves`, `cisa_kev_vulnerabilities` | Latest accepted state | Low-latency serving tables |
| `cisa_kev_changes` | Retained | Explainable snapshot-change history |
| `epss_scores` | Latest 30 inclusive source dates by default | Bounds PostgreSQL growth while supporting short trends |
| `epss_daily_summaries` | Retained | Compact long-term trend evidence |
| Airflow metadata/XCom | Configurable maintenance retention | Limits operational metadata growth |
| Database backups | Configured operational retention with checksum validation | Recovery without indefinite uncontrolled accumulation |

Before production deployment, owners must approve Raw retention, backup retention, recovery
objectives and any legal hold requirements. The target S3 design adds versioning and explicit
lifecycle rules rather than silently inheriting the local indefinite policy.

Validated S3 Bronze objects are recovery and audit copies. An upload must be checksum-verified
and represented in `raw_artifact_locations`; object presence alone is not acceptance evidence.
S3 must not trigger a parallel normalization path while Airflow owns orchestration. Before any
local cleanup is enabled, complete a restore/replay drill from S3 and document the minimum local
retention window. Production rollout should add least-privilege access, upload/verification
failure alerts, and appropriate CloudTrail data-event or S3 access telemetry after reviewing its
cost and retention implications.

## Responsible interpretation

- CVSS is technical severity, not probability or organisational risk.
- EPSS is an estimated 30-day exploitation probability, not impact or proof of exploitation.
- CISA KEV is evidence of exploitation in the wild, not proof that a particular environment
  contains the affected product.
- ThreatFlow outputs are investigation aids. Remediation decisions require asset presence,
  exposure, business impact, compensating controls and validation by security staff.
- Missing cross-source matches must be displayed as missing context, not converted to zero
  risk.

## Incident and correction handling

Invalid or implausibly incomplete source payloads must fail ingestion and retain Raw evidence
for investigation. Corrections are applied through replay/upsert, never manual table edits or
truncation. Logs must identify the source, stage, interval/hash and safe record counts without
printing secrets or full feeds.
